# 经历与技能写法

本文件把通用原则落到实习、项目和技能栏的具体写法。它不替代项目事实，也不提前生成任何项目终稿。

## 一段经历的基本结构

根据版面和岗位选择以下信息：

1. **名称、时间、身份**：名称可以不同于仓库名，但必须准确；时间、单位、身份和参与程度以核实资料为准。
2. **项目简介**：用一句话说明业务定位和有依据的差异点。项目背景可以交代服务对象或约束，但不写成产品说明书。
3. **相关技术栈**：只保留与目标岗位和核心贡献有关的技术。项目用过不等于本人掌握，更不等于熟练；部署工具、迁移工具和运行环境版本只在与贡献有关时出现。
4. **核心贡献**：围绕一两条业务主线取舍。每条尽量回答“遇到什么问题或约束、本人采取了什么关键动作、实现或验证了什么结果、依据在哪里”。句式可以变化，不要求每条机械套同一模板。

项目正文不放类名、内部接口名、方法名、源码路径和测试文件名；这些保留在项目素材中作为面试准备证据。

## 实习与项目的边界

- 实习优先写真实参与的业务、任务和协作方式；普通实习生不写整个系统负责人，除非有明确证据支持主导范围。
- 团队共同完成的功能要说明本人负责的子范围；“参与”“负责”“设计”“主导”“独立完成”按证据强度选词。
- 个人项目可以写完整链路，但要区分自己实现的部分、引用的组件或模型、课程/历史参考代码和实际交付状态。
- 约三个月主力经历参考约六条，四到六个月且投入较深的主力项目最多约八条，补充项目约三条；这是版面参考，不足则不凑数。

## 业务主线与条目组织

先列出两三条候选业务线，再选择一两条能从业务问题讲到技术方案和验证结果的主线。条目之间要共同支撑同一业务流程；横切能力只有服务于主线时才写。

推荐保留的证据类型包括：需求约束、数据或状态流转、异常与边界处理、并发/事务/权限/稳定性治理、可观测性、测试验证、部署交付和问题排查。没有证据时只保留事实描述，不把概念写成成果。

## RAG / Agent 项目的写法

只在项目确实具备且本人能讲清时记录：

- 业务场景、用户或使用对象，以及 RAG/Agent 解决的具体问题；
- 文档或数据接入、解析、切分、索引、检索、重排、引用、上下文或工具调用中本人负责的环节；
- 选择某种方案的约束和取舍，而不是只罗列框架名；
- 评测集、错误案例、质量指标、日志追踪、失败兜底、部署或交付形态等可验证信息；
- 模型来源、外部组件和团队边界。

“接入大模型”“完成向量化”“实现 Agent”本身不是完整贡献条目。没有业务评估或真实验证时，不补准确率、召回率、延迟和用户规模。

## AI Coding 与跨领域能力的写法

把工具使用还原为研发行为：需求澄清与拆解、任务边界控制、方案判断、AI 产出审查、错误定位、测试/手动验证、风险修正和交付。不要把“使用 Codex/Claude Code”单独当成成果，也不直接写“同龄人领先”。

sEMG 项目可体现数据、推理、状态管理、GUI、服务和交付形成的系统链路，但必须区分模型或组件来源，不把端到端系统工程写成从零训练模型。

## 技能栏的组织

技能栏只保留与目标岗位相关、且能由项目、实习、课程或持续实践支撑的能力。建议按“语言与基础、后端框架/数据与中间件、AI 应用、研发工具”分组，具体分组随实际技能数量调整。

为每项候选技能保留四个内部判断：支撑来源、本人实际掌握程度、可解释的简历表述、尚待确认的问题。只使用“掌握程度”与证据相称的词，不能由仓库依赖或一次调用推导“熟练掌握”。项目技术栈与最终技能栏分开维护。

## 面试追问入口

每个采用的条目只保留一两个与其直接相关的追问入口，例如方案取舍、异常处理、验证方法、边界条件或结果依据。追问入口服务于准备面试，不扩展成通用八股题库；无法讲清的内容不进入当前简历。
